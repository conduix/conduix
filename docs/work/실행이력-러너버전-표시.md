# 작업 지시 — 실행 이력에 러너 버전/이미지를 항상 남긴다

작성 2026-09-10 / 상태: 미착수

## 한 줄 요약

**무엇으로 실행됐는지가 이력에 안 남는 실행이 있다.**
GUI 의 Runner Version 이 공란으로 뜨고, 사후에 재현·디버깅할 근거가 없다.

## 재현

1. 커스텀 native stage 를 쓰지 않는 워크플로를 실행한다
   (예: `[batch] 아동복지급식 가맹점 → MySQL`)
2. GUI 워크플로 상세 → **Runner Version 이 비어 있다**

실측: `workflow_executions` 50건 중 **4건만** `runner_version_id` 가 채워짐 (8%)

---

## 원인

### 실행 경로는 두 갈래인데 한쪽만 기록된다

`control-plane/internal/services/runner_resolver.go:158`

```go
func (r *RunnerResolver) ResolveRunnerVersion(workflow *models.Workflow) (string, string, bool, error) {
    nativePlugins, err := r.findNativePluginsInWorkflow(workflow)
    ...
    if len(nativePlugins) == 0 {
        return "", DefaultRunnerImage, false, nil
        //      ↑ 버전 ID 는 빈 문자열, 이미지만 반환
    }
    ...
}
```

| 실행 형태 | 실제 실행 대상 | 이력 기록 |
|---|---|---|
| 커스텀 stage 있음 | `runner_versions.Binary` (initContainer 주입) | `runner_version_id` ✅ |
| **커스텀 stage 없음** | **`ghcr.io/conduix/pipeline-runner:latest`** | **아무것도 없음** ❌ |

둘 다 "무언가로 실행"됐는데 후자만 공란이다.

### 반환된 이미지를 모든 호출부가 버린다

```go
versionID, _, _, rerr := h.runnerResolver.ResolveRunnerVersion(&workflow)
//          ↑ DefaultRunnerImage 가 여기서 사라진다
```

호출부 6곳 전부 두 번째 반환값을 `_` 로 받는다:

```
control-plane/internal/api/handlers/workflow_start.go:76
control-plane/internal/api/handlers/workflow.go:797, 887, 965
control-plane/internal/services/scheduler_service.go:459, 530
```

### 저장할 자리도 없다

- `models.WorkflowExecution` — `RunnerVersionID` 만 있고 이미지 필드가 없다
- `pipeline_runs.runner_image` — 컬럼은 있으나 **테이블 행이 0건** (안 쓰이는 경로로 보임)

### `latest` 는 추적에 쓸 수 없다

태그가 가리키는 다이제스트는 계속 바뀐다. `latest` 라고만 남겨도
"그때 무슨 바이너리였는지" 는 알 수 없다. **다이제스트가 필요하다.**

---

## 참고 — 오해하기 쉬운 지점 두 가지

조사 중 확인한 사실이다. 이 작업의 전제이므로 적어둔다.

**① 빌드는 워크플로별로 하지 않는다**

`runner_builder.go:185`
```go
rb.db.Where("type = ? AND status = ?", "native", "active").Find(&plugins)
```
활성 native plugin **전부**를 한 바이너리로 컴파일한다.
실측: 빌드 18회, 모두 같은 플러그인 1개(`geocode_kakao`)를 담고 있다.

**② `latest` 이미지는 지우면 안 된다**

이미지는 **베이스**이고 커스텀 바이너리는 initContainer 가 `/runner` 에 내려놓는다
(`pipeline-worker/internal/k8s/job_manager.go:394`).

```go
func (m *JobManager) injectRunnerBinary(ps *corev1.PodSpec, runnerVersionID, image string, ...) {
    if runnerVersionID == "" {
        return   // 주입 생략 → 이미지의 기본 바이너리로 실행
    }
    ...
}
```

즉 파드 이미지가 `latest` 인 것 자체는 정상이다. 지우면 커스텀 stage 를 쓰지 않는
워크플로가 전부 실행 불가가 된다.

## 해야 할 것

### 방향 A — 이미지도 기록 (최소)

이미 반환하고 있는 값을 버리지 말고 저장한다.

1. `models.WorkflowExecution` 에 `RunnerImage string` 추가 + 마이그레이션
   (현재 최신 `000008`, → `000009_add_execution_runner_image`)
2. 호출부 6곳에서 두 번째 반환값을 받아 execution 에 저장
3. `RunnerDeploymentRow` 에 `runner_image` 추가 → GUI 표시

**한계**: `latest` 라고만 남으면 재현에 부족하다. 다이제스트까지 남겨야 실질적이다.

### 방향 B — 항상 최신 ready 바이너리 주입 (권장)

바이너리가 어차피 **전체 플러그인이 든 하나**이므로, 워크플로별로 주입 여부를
가릴 이유가 약하다.

```
지금:  커스텀 stage 쓰면 주입, 아니면 이미지 기본 바이너리
바꾸면: 항상 최신 ready 바이너리 주입
```

**얻는 것**
- `runner_version_id` 가 항상 채워진다 → 이력·재현·stale 판정이 일관됨
- 워크플로 설정에 커스텀 stage 를 추가해도 리졸버 판단 없이 바로 동작
- 실행 대상이 한 종류로 수렴 → "이미지냐 바이너리냐" 분기가 사라짐

**치르는 것**
- 커스텀 stage 안 쓰는 워크플로도 initContainer 1개 추가 (바이너리 ~123MB 전송)
- ready 버전이 하나도 없는 초기 상태 처리 필요 → 그때만 이미지 폴백

> 결정 필요: B 로 갈 때 "ready 버전 없음" 을 빌드 필요로 볼지, 이미지 폴백으로 둘지.
> 폴백을 둔다면 그 경우에도 이미지+다이제스트를 기록해야 A 의 문제가 남지 않는다.

### 공통 — 다이제스트 기록

어느 방향이든, 이미지로 실행되는 경로가 남는다면 **태그가 아니라 다이제스트**를
기록해야 한다. `runner_versions.image_digest` 컬럼이 이미 있으니 같은 방식으로 둔다.
