# 공중화장실 지오코딩 — 알고리즘·파이프라인·실패 케이스

전국공중화장실표준데이터는 좌표를 제공하지 않아 주소로 좌표를 만들었다.
이 문서는 **어떻게 좌표를 만들었는지**와 **끝내 만들지 못한 주소**를 남긴다.

조사일 2026-09-03 / 지오코더: Kakao Local API

## 원칙 — 근사 좌표는 쓰지 않는다

**화장실은 급히 찾는 시설이다.** 수백 m 어긋난 위치를 알려주면 안 가느니만 못하다.
그래서 번지를 특정하지 못한 주소는 **동 중심점 같은 근사 좌표로 채우지 않고 실패로 남긴다.**

실제로 동 중심점으로 620건을 채웠다가 전부 되돌렸다.
성공률은 99.15% → 97.99% 로 내려갔지만, **남은 좌표는 전부 번지 단위로 정확하다.**

> 성공률 수치를 높이려고 부정확한 좌표를 섞는 것은 데이터 품질을 감추는 것이다.
> 실패는 실패로 세어야 나중에 고칠 수 있다.

## 결과

| 구분 | 건수 | 비율 |
|---|---|---|
| 전체 레코드 | 53,572 | 100% |
| **좌표 확보 (번지 단위 정확)** | **52,494** | **97.99%** |
| 좌표 실패 | 1,078 | 2.01% |

주소 기준으로는 고유주소 44,299건 중 **925건**이 실패했다.
(레코드가 1,078건인 것은 같은 실패 주소를 여러 화장실이 공유하기 때문이다)

### 단계별 복구

| 단계 | 방법 | 복구 | 누적 |
|---|---|---|---|
| 1차 | 원본 주소 그대로 | 42,466 | 96.1% |
| 2차 | 띄어쓰기·지번폴백·행정구역보강·부번탐색 | +609 | 97.6% |
| 3차 | `N번지 M호` → `N-M` 표기 정규화 | +122 | **97.99%** |
| ~~동 중심점~~ | ~~번지 못 찾으면 동 중심~~ | ~~+620~~ | **폐기** |

2차의 **부번 탐색**(`399` 실패 → `399-1` 시도)이 실제로 기여했다.
번지가 미등록이어도 부번은 등록된 경우가 있다.

### 좌표 정확도

| 등급 | 건수 | 의미 |
|---|---|---|
| `road_addr` / `road` | 43,684 | 도로명 정확 매칭 |
| `region_addr` / `region` | 8,810 | 지번 정확 매칭 |

**근사 좌표는 하나도 없다.** 지도에 찍힌 위치는 전부 번지 단위다.

## 처리 흐름과 알고리즘

### 설계 원칙

**① 비싼 호출은 마지막에.** 무료·무제한 연산(정규화·캐시 조회)으로 최대한 걸러내고,
쿼터가 있는 API는 남은 것에만 쓴다. 쿼터가 적은 API일수록 뒤에 둔다.

**② 정확한 방법부터.** 도로명 → 지번 → 표기교정 → 부번탐색 순.
먼저 성공하면 뒤 단계는 호출하지 않는다.

**③ 근사 좌표는 성공이 아니다.** 번지를 특정하지 못하면 실패로 남긴다.
동 중심점으로 채우면 성공률 수치만 오르고 데이터 품질은 내려간다.

**④ 상태를 외부에 둔다.** 진행 상황이 캐시 테이블에 있으므로 중단·재개가 자유롭다.

### 전체 흐름

```
레코드 53,572
    │
    ├─[G1] 주소 단위 중복 제거 ──────────────► 44,790  (-8,782)
    │      같은 건물에 화장실 여러 개
    │
    ├─[G2] 정규화 후 재중복 제거 ────────────► 44,299  (-491)
    │      표기만 다르고 같은 주소
    │
    ├─[G3] 캐시 조회 (재실행 시) ────────────► 미처리분만
    │
    ├─[S1] 카카오 1차: 원본 주소 ────────────► 42,466 성공
    │
    ├─[S2] 카카오 2차: 폴백 4종 ─────────────► +609
    │      띄어쓰기 / 지번주소 / 행정구역보강 / 부번탐색
    │
    ├─[S3] 카카오 3차: 번지표기 정규화 ──────► +122
    │      'N번지 M호' → 'N-M'
    │
    ├─[G4] 주소 파손 판정 ───────────────────► 100건 배제
    │      서술형·시도누락·공백없음·복수필지
    │      → 어느 API 도 못 찾는다. 네이버 쿼터를 쓸 이유가 없다
    │
    └─[S4] 네이버: 825건만 ──────────────────► 전체의 1.5%
           카카오 DB 에만 없는 주소
```

**G4가 이 설계의 핵심이다.** 실패 925건을 전부 네이버로 넘기지 않는다.
주소 문자열 자체가 깨진 100건은 지오코더를 바꿔도 결과가 같으므로 미리 뺀다.

| | 네이버 호출량 |
|---|---|
| 게이트 없이 전량 | 53,572건 |
| 캐시만 적용 | 44,299건 |
| **전체 게이트 적용** | **825건 (1.5%)** |

### 폴백 알고리즘

`resolve(주소)` — 성공하는 즉시 반환한다.

```
① 원본 그대로
② 띄어쓰기 교정      '수리골길17'    → '수리골길 17'
                     '18번길 21'     → '18번길21'
③ 지번주소로 재시도   road_addr 오염 대비 (657건 발견)
④ 행정구역 보강      '가좌4동 399'
                       → '가좌4동' 조회 → region_1depth/2depth 획득
                       → '인천 서해구 가좌4동 399' 재조회
⑤ 번지표기 정규화    '502번지 59호'  → '502-59'
                     '산 52번지 18호' → '산52-18'
⑥ 부번 탐색         '399' 실패 → '399-1' ~ '399-5' 순차 시도
                     번지는 미등록이어도 부번은 등록된 경우가 있다
──────────────────── 여기까지 실패하면 실패로 확정
✗ 동 중심점          쓰지 않는다 (원칙 ③)
```

각 단계의 실측 기여도는 [단계별 복구](#단계별-복구) 표 참조.

### 주소 정규화 규칙

지오코딩 전 공통 적용. 원본 표기가 지오코더를 방해하는 것만 제거한다.

| 규칙 | 예 | 이유 |
|---|---|---|
| 쉼표 뒤 절단 | `도농1길 69, 화장실` → `도농1길 69` | 건물설명이 매칭 방해 |
| 괄호 제거 | `삼양로 78 (길음동)` → `삼양로 78` | 법정동 병기가 매칭 방해 |
| 번길+번지 분리 | `구즉로58번길15-12` → `구즉로58번길 15-12` | 붙어 있으면 미매칭 |
| 연속 공백 정리 | `로  15` → `로 15` | |

**주의**: 번길 표기는 데이터마다 반대로 틀려 있다(붙여야 할 것이 떨어져 있고, 그 반대도 있다).
한 방향으로만 고치면 다른 쪽이 깨지므로 **양쪽 변형을 폴백으로 순차 시도**한다.

### 주소 파손 판정 (G4)

다음 중 하나라도 해당하면 지오코더를 바꿔도 실패한다. 네이버로 넘기지 않는다.

| 판정 | 예 | 건수 |
|---|---|---|
| 서술형 위치로 끝남 | `태평인라인장 앞`, `조사리 해안가` | 12 |
| 시도명 누락 | `남문로 352` | 19 |
| 공백 없는 주소 | `경상남도마산합포구제2두부로30` | 30 |
| 복수 필지 | `583-2외 8필지` | 6 |
| 괄호 안 닫힘 | `고덕로 283(좌교리` | 일부 |

이 판정은 **보수적으로** 한다. 애매하면 네이버로 보낸다 —
쿼터 1건보다 좌표 1건이 비싸다.

### 지오코더 배치 순서

쿼터가 많고 제약이 적은 것을 앞에 둔다.

| 순서 | 지오코더 | 일 한도 | 담당 | 실측 |
|---|---|---|---|---|
| 1 | **Kakao** | 100,000 | 전량 | 97.9% 처리 |
| 2 | **Naver** | 확인 필요 | 카카오 실패분 중 주소 정상 | 825건 |
| — | ~~VWorld~~ | 40,000 | **사용 불가** | 약관상 DB 저장 금지 |
| — | ~~Nominatim~~ | 사실상 불가 | 표본 성공률 80% | 정책상 대량 불가 |

**네이버를 뒤에 두는 이유**: 쿼터 정책을 확인하지 못했다.
카카오(10만/일)보다 여유가 없다고 보고, 최소 호출로 설계한다.

> **미검증**: 네이버 Geocoding API 의 실제 성공률을 측정하지 못했다(키 없음).
> 825건 중 몇 건을 건질지는 실행해봐야 안다. "카카오에 없으면 네이버에 있다" 는
> 보장이 아니라 가능성이다.

## conduix 파이프라인 내재화

위 알고리즘을 일회성 스크립트가 아니라 **재사용 가능한 스테이지**로 만든다.
좌표 없는 공공데이터는 공중화장실만이 아니다 — 착한가격업소도 주소만 준다.

### 먼저 알아야 할 것 — 실행 경로가 3개다

conduix 에는 스테이지 실행 경로가 셋 있고, **커스텀 스테이지를 붙일 수 있는 곳은 하나뿐이다.**

| 경로 | 위치 | 커스텀 `type` |
|---|---|---|
| **stream 레지스트리** | `pipeline-core/pkg/stream/` | ✅ **여기** |
| executor `applyStage` | `pkg/executor/group_executor.go:1187~` | switch 하드코딩, default 로 위임 |
| v2 config `StepV2` | `pkg/config/v2_config.go:520` | ❌ **불가** |

**`steps:` 로는 지오코딩 스테이지를 쓸 수 없다.** `StepV2` 구조체에 `Type` 필드가 아예 없다.

```go
// pipeline-core/pkg/config/v2_config.go:520
type StepV2 struct {
    Name      string
    Transform string        // Bloblang
    Filter    FilterConfig
    Sample    float64
    Select    []string
    Exclude   []string
}   // ← Type 없음. transform/filter/sample/select/exclude 5종 고정
```

`type` 을 쓰려면 `stages:` 경로여야 한다.

```go
// shared/types/hierarchy.go:168
type Stage struct {
    ID     string
    Name   string
    Type   string          // ← 이것
    Config map[string]any
}
```

> **확인 못 함**: `stages:` 형식을 **파일 YAML** 로 로드하는 로더를 찾지 못했다.
> GUI/DB 저장 경로만 확인됐다. 파일로 돌리려면 로더 확인이 선행돼야 한다.

### 기존에 재사용할 것

외부 조회 스테이지가 이미 4종 있다. 지오코딩과 성격이 같다.

| 스테이지 | 파일 | 쓸 수 있는 것 |
|---|---|---|
| `lookup_enrich` | `lookup_enrich_stage.go` | HTTP/SQL 조회, LRU 캐시, TTL, `on_missing` |
| `batch_lookup` | `batch_lookup_stage.go` | 배치 버퍼링 |
| `async_enrich` | `async_enrich_stage.go` | 워커풀 병렬 |
| `es_lookup` | `es_lookup_stage.go` | ES 조회 |

**`lookup_enrich_stage.go` 를 템플릿으로 복사해 시작한다.** 캐시·HTTP·SQL·`onMissing` 골격이 그대로다.

```go
// lookup_enrich_stage.go:19 — 지오코딩에 필요한 것이 이미 다 있다
type LookupEnrichStage struct {
    BaseStage
    sourceType   string        // redis, http, sql
    onMissing    string        // skip, error, default
    timeout      time.Duration
    httpClient   *http.Client
    sqlDB        *sql.DB
    cacheEnabled bool
    cacheTTL     time.Duration
    cache        *lruCache     // sync.RWMutex 로 보호됨
}
```

### 직접 만들어야 하는 것

기존 스테이지에 **없는** 것들이다. 지오코딩에는 필수다.

| 필요 | 현황 | 비고 |
|---|---|---|
| **rate limiter** | ❌ 없음 | `async_enrich`·`batch_lookup` 은 동시성(workers=4)만 제한. 초당 호출량 제한 없음 |
| **retry / backoff** | ❌ 없음 | `lookup_enrich` 에 retry 코드 0건. HTTP 실패 시 1회로 끝 |
| **일일 쿼터 추적** | ❌ 없음 | |
| **주소 정규화** | ❌ 없음 | |

`throttle_stage.go` 가 있으나 파이프라인 전체 흐름 조절용이지 특정 스테이지의 API 호출 제한이 아니다.

> **429(쿼터 초과) 재시도가 없다는 게 특히 중요하다.** 카카오·네이버 모두 쿼터를 넘기면 429 를
> 주는데, 재시도가 없으면 그 레코드는 그냥 실패로 남는다. 지수 백오프를 직접 넣어야 한다.

### 인터페이스와 등록

```go
// pipeline-core/pkg/stream/types.go:27
type Stage interface {
    Name() string
    Type() string
    Process(ctx context.Context, record *Record) (*Record, error)  // nil 반환 = 레코드 제거
    Close() error
}
```

`BaseStage` 를 embed 하면 `Name()`/`Type()`/`Close()` 와 통계 카운터를 얻는다.

**등록은 두 곳이다** — factory 와 GUI 스키마가 분리돼 있다.

```go
// ① pipeline-core/pkg/stream/stage.go 의 init()  — 실행에 필요
RegisterStageFactory("geocode", func(n string, c map[string]any) (Stage, error) {
    return NewGeocodeStage(n, c)
})

// ② pipeline-core/pkg/stream/stage_registry.go 의 init()  — GUI 노출에 필요
StageRegistry.Register(GeocodeStageSchema())
```

①만 하면 동작하지만 GUI 에 안 보이고, ②만 하면 GUI 에 보이지만 실행이 안 된다.
실제로 `lookup_enrich` 등 11종이 ①만 돼 있어 GUI 에 없다.

### 스테이지 구성 — 3개로 나눈다

책임이 다르고 **쿼터 정책도 다르므로** 하나로 합치지 않는다.

```
geocode            1차: 주 지오코더 (카카오)
geocode_fallback   2차: 폴백 변형 재시도
geocode_secondary  3차: 보조 지오코더 (네이버) — 게이트 통과분만
```

나누면 **설정만으로 3차를 끄고 켤 수 있다.** 네이버 쿼터가 빠듯한 날은 빼면 된다.

### 설정 예시

```yaml
stages:
  # ── G1/G2: 주소 정규화 + 중복 제거 ─────────────────────
  - name: normalize-address
    type: remap
    config:
      # 쉼표 뒤 건물설명·괄호 제거. 정규화 규칙은 위 '주소 정규화 규칙' 참조
      addr_norm: 'normalize_addr(coalesce(.road_addr, .lotno_addr))'

  - name: unique-address
    type: dedupe
    config:
      key_fields: [addr_norm]
      strategy: keep_first          # 53,572 → 44,299

  # ── S1: 카카오 1차 ────────────────────────────────────
  - name: kakao-primary
    type: geocode
    config:
      provider: kakao
      address_field: addr_norm
      output: { lat: lat, lon: lon, match_type: geo_match }
      cache:
        enabled: true
        source: sql                  # 영속 캐시 (프로세스 죽어도 유지)
        driver: mysql
        table: geocode_cache
        key_field: addr_norm
        memory_lru: 10000            # 1차 핫 캐시
      rate_limit: { rps: 30, concurrency: 8 }
      retry: { max: 3, on: [429, 500, 502, 503], backoff: exponential }
      daily_quota: 100000
      on_missing: continue           # 실패해도 레코드는 흘려보낸다

  # ── S2: 폴백 변형 (1차 실패분만) ──────────────────────
  - name: kakao-variants
    type: geocode_fallback
    config:
      provider: kakao
      when: 'lat == null'            # 좌표 있으면 건너뜀
      strategies:                    # 순서대로, 먼저 되면 중단
        - spacing                    # 번길 붙임/띄움 양방향
        - lotno_address              # 지번주소로 재시도
        - region_prefix              # 행정구역 조회 후 접두어 보강
        - lot_notation               # 'N번지 M호' → 'N-M'
        - sublot                     # 'N' → 'N-1' ~ 'N-5'
      on_missing: continue

  # ── G4: 주소 파손 판정 ────────────────────────────────
  - name: mark-unfixable
    type: remap
    config:
      # 여기 걸리면 지오코더를 바꿔도 실패한다. 네이버로 넘기지 않는다.
      geo_unfixable: |
        .lat == null && (
          .addr_norm.re_match("(인근|부근|일대|앞|옆|뒤|해안가|마을|입구|주변|밑|내)$")
          || !.addr_norm.re_match("^(서울|부산|대구|인천|광주|대전|울산|세종|경기|강원|충청|충북|충남|전라|전북|전남|경상|경북|경남|제주)")
          || .addr_norm.re_match("^\\S{10,}$")
          || .addr_norm.re_match("외\\s*\\d*\\s*필지")
          || (.addr_norm.contains("(") && !.addr_norm.contains(")"))
        )

  # ── S3: 네이버 (게이트 통과분만) ──────────────────────
  - name: naver-fallback
    type: geocode_secondary
    config:
      provider: naver
      when: 'lat == null && geo_unfixable != true'   # ← 핵심 게이트
      address_field: addr_norm
      cache: { enabled: true, source: sql, table: geocode_cache, key_field: addr_norm }
      rate_limit: { rps: 10, concurrency: 4 }        # 카카오보다 보수적
      retry: { max: 3, on: [429], backoff: exponential }
      daily_quota: ${NAVER_DAILY_QUOTA}
      on_quota_exceeded: stop        # 소진 시 중단 — 다음 실행이 이어감
      on_missing: continue
```

### 네이버 호출을 최소로 유지하는 장치 5가지

**① `when` 이중 게이트**

```yaml
when: 'lat == null && geo_unfixable != true'
```

좌표가 있으면 안 부르고, 주소가 깨졌으면 안 부른다.
실측 **925건 중 825건만** 통과한다.

**② 공유 캐시 테이블**

`geocode_cache` 를 카카오·네이버가 **같이 쓴다.** `provider` 로 누가 찾았는지 구분한다.
재실행 시 이미 좌표가 있는 주소는 어느 쪽도 다시 부르지 않는다.

```sql
addr_norm(PK) · lat · lon · provider · match_type
status(ok/not_found/unfixable/error) · attempts · last_error
```

**③ `unfixable` 영구 기록**

파손 판정된 주소는 `status='unfixable'` 로 남아 **다음 실행에서 재시도하지 않는다.**
원본 데이터가 고쳐지면 그때 상태를 되돌려 재시도한다.

**④ `daily_quota` + `on_quota_exceeded: stop`**

쿼터 초과는 에러가 아니라 정상 중단이다. 처리한 만큼 저장되고 다음 실행이 이어간다.

**⑤ 순서 자체가 장치다**

| 배치 | 네이버 호출량 |
|---|---|
| 네이버를 1차로 | 53,572 |
| 캐시만 적용 | 44,299 |
| **현재 설계** | **825 (1.5%)** |

**65배 차이**가 순서와 게이트에서만 나온다.

### 구현 시 주의

**① 캐시는 SQL(영속) 이 본체, LRU 는 핫 캐시.**
`lookup_enrich` 의 `lruCache` 만 쓰면 프로세스가 죽을 때 진행 상황이 날아간다.
DB 테이블을 본체로 두고 LRU 를 앞에 세운다.

**② 스테이지 인스턴스는 실행당 1회 생성되어 재사용된다.**
`group_executor.go:1349` 의 `getOrCreateStreamStage()` 가 `type\x00name` 키로 캐싱하고,
`closeStreamStages()` 가 종료 시 `Close()` 한다.
→ DB 풀·HTTP 클라이언트를 스테이지가 들고 있어도 레코드마다 재생성되지 않는다.

**③ `Process()` 는 병렬 호출된다.** 내부 상태는 스레드 안전해야 한다.
`lruCache` 가 `sync.RWMutex` 를 쓰는 이유다.

**④ 레코드 단위 인터페이스지만 API 호출은 묶어야 한다.**
`batch_lookup_stage.go` 의 버퍼링 패턴을 참고한다.
실측상 배치화로 **2.3건/s → 65건/s (26배)** 개선됐다.

**⑤ 한반도 범위 밖 좌표는 버린다.**
```
lat 33.0~39.6 / lon 124.5~132.0
```
지오코더가 동명 지역을 물어오는 경우가 있다 —
실측: '가좌어린이공원' 검색이 서울 서대문구 것을 반환(인천 대상, **27km 오차**).

**⑥ `on_missing: continue` 가 기본이다.**
좌표를 못 찾았다고 레코드를 버리면 안 된다. 이름·주소·속성은 여전히 쓸모 있다.
지도에 못 찍을 뿐이다.

### 네이티브 플러그인으로 만들 경우

`plugin-sdk/native_stage.go` 의 인터페이스는 **`context.Context` 가 없다.**
타임아웃·취소를 스테이지 내부에서 직접 관리해야 한다.

```go
type NativeStage interface {
    Init(config map[string]any) error
    Process(record map[string]any) (map[string]any, error)
    ProcessBatch(records []map[string]any) ([]map[string]any, error)
    Close() error
}
```

**주의**: 어댑터(`native_stage_adapter.go:78`)가 **에러 시 원본 레코드를 그대로 통과**시킨다.

```go
result, err := a.native.Process(record.Data)
if err != nil {
    a.incrementError()
    return record, nil   // ← 에러가 묻힌다
}
```

지오코딩 실패를 파이프라인에서 잡으려면 **에러 대신 레코드에 실패 마커 필드**를 넣는다.

**import 제약**: 표준 라이브러리와 conduix 내부 모듈은 자유롭지만, 외부 모듈은
`allowed_modules` 테이블 등록이 필요하다(`stage_import_validation.go:16`).
`net/http`·`database/sql`·`encoding/json` 만 쓰면 문제없으나,
MySQL 드라이버나 `golang.org/x/time/rate` 를 쓰려면 등록해야 한다.

**JavaScript(`js_script`) 는 쓸 수 없다.** 등록된 Go 헬퍼가 `console.log` 하나뿐이라
외부 API 호출 수단이 없고, 레코드당 1초 타임아웃에 VM 을 `sync.Pool` 로 돌려쓴다.

## 원본 데이터에서 발견한 문제

지오코딩 실패와 별개로, 수집 단계에서 확인된 것들이다.

**① `road_addr` 칸에 지번주소가 들어있다 — 657건**

```
road_addr : 가좌4동 399                    ← 도로명이 아님
lotno_addr: 인천광역시 서해구 가좌동 399    ← 이쪽이 정상
```
그중 65건은 `lotno_addr`이 정상이라 폴백으로 복구했다.
**도로명주소 칸을 무조건 신뢰하면 안 된다.**

**② 개방시간(`opn_hr`)은 시각이 아니라 등급값이다**

| 값 | 건수 |
|---|---|
| 정시 | 25,326 |
| 상시 | 22,305 |
| 불규칙 | 861 |
| **미개방** | **576** |

`미개방` 576건은 지도에 그대로 띄우면 안 된다. 갔는데 닫혀 있는 것이 최악이다.

**③ 같은 주소에 화장실이 여러 개 있다**

레코드 53,572건 → 고유주소 44,299건. 주소 단위로 캐시하면 호출이 **17% 줄어든다.**
